# Structural Verification as a Substitute for Model Capability: A Deterministic Reliability Layer for Multi-Agent Research Agents on Local LLMs

**Gabri Elles**
*DeepDelve project, [github.com/g0elles/deepdelve](https://github.com/g0elles/deepdelve)*

## Abstract

Open-ended research agents have no natural pass/fail oracle. A coding agent can run its test suite; a research agent asked to explain a historical or technical question has no equivalent check, and by the time it fabricates a citation, drops half the query, or contradicts one of its own sources, the error is already synthesized into fluent prose. This problem is sharper on local, sub-30B-parameter models than on frontier hosted systems, and most published deep-research architectures assume the latter. We present DeepDelve, a multi-agent research assistant built to run entirely on a single 16GB-VRAM consumer GPU against `gpt-oss:20b`. Our central finding, reached empirically across a documented incident history, is that prompt-only reliability fixes do not hold on a model of this class; every durable fix instead moved enforcement out of the prompt and into deterministic code. We describe the resulting verification layer, seven mechanisms including a priority-ordered bank of 27 structural checks, starvation guards for that priority queue, fresh-context independent review, and deterministic salvage for known failure modes, together with the incidents that motivated each one. For two of these mechanisms we report a controlled ablation showing they are causally load-bearing rather than incidentally correlated with a successful run: removing them drops mean benchmark score from 0.75 to 0.25 and 0.125 respectively. We position the contribution honestly against prior art: no individual mechanism is new, but the specific combination, hardened for the local sub-30B regime, has no documented precedent in the systems we surveyed. We close with the approach's limitations, stated without qualification: the verification layer is reactive, not proactive, and cannot rescue a model below some capability floor, only label its failure honestly instead of accepting it silently.

## 1. Introduction

A coding agent asked to fix a bug has a built-in oracle: run the test suite, and it either passes or it doesn't. A research agent asked an open-ended question, to explain the causes of a historical event or synthesize the state of a technical field, has no equivalent. There is no test to run against a claim about the fall of the Roman Empire. The only available signal is whether the agent's own process was sound: whether every citation resolves to something it actually fetched, whether its claims are supported by what it read, whether it addressed the whole question rather than a fraction of it. By the time any of these checks fails, the error is already synthesized into prose that reads as confident and complete.

Most published deep-research architectures address this by assuming a frontier-class generator, or by treating reliability as a property of training rather than something the runtime enforces. GPT Researcher, Stanford STORM, `dzhng/deep-research`, Tongyi DeepResearch, CrewAI, AutoGen/AG2, CAMEL-AI, LangGraph's Corrective RAG pattern, and the published deep-research systems from Perplexity and OpenAI were all built around, or evaluated against, capable hosted models. None targets the regime this project operates in: a roughly 20B-parameter model, served locally on a single consumer GPU, performing open-ended multi-hop research with no fallback to a larger model mid-run.

Our repeated finding, reached empirically rather than assumed at the outset, is that prompt-only fixes do not survive contact with this failure class at this model size. The project's own incident history documents the same lesson relearned in different forms at least half a dozen times. A model instructed not to cite a source it was never given cites it anyway. A model told to stop delegating once research is sufficient loops past that point regardless. A model warned, inline, in its own evidence base, that a specific citation does not match anything fetched this run, cites it again on the very next independent dispatch. Each failure was first addressed as a prompt fix, and each prompt fix was falsified by a live run before a structural one was built instead. The organizing principle that emerged, and that the rest of this paper follows from, is: where a prompt instruction can be silently ignored, remove the capability that allows it to be ignored, or verify the output with code that runs regardless of whether the instruction was honored.

This paper makes three contributions. First, we describe seven verification mechanisms, each motivated by a specific, dated production incident rather than a generic taxonomy of possible failures (Section 3). Second, we report a controlled ablation of two of these mechanisms, distinguishing genuinely load-bearing structure from what Jwalapuram et al. (2026) term "expensive witnesses": complexity that carries real overhead but contributes little to the measured outcome (Section 4). Third, we position the work against prior art without overclaiming: individual components have precedent, but the specific combination, hardened for the sub-30B local regime, does not (Section 5).

## 2. System Architecture

DeepDelve runs entirely against local, OpenAI-compatible model servers, defaulting to Ollama, with `gpt-oss:20b` as the current validated baseline on a single 16GB-VRAM-class GPU. This baseline is consistent with published capacity-floor evidence placing roughly 14B parameters as the minimum threshold for reliable tool invocation in comparable agentic settings (Huang, Malwe, & Wang, 2025). No component of the architecture assumes access to a larger or hosted model at any point during a run.

The system is a typed, three-tier delegation hierarchy. A Planner agent plans in bounded, named slots rather than an open-ended task list, delegates work to specialist agents, and adaptively replans when results reveal gaps or contradictions. Two Tier-2 specialists, WebSearcher and AcademicSearcher, conduct search and retrieval. Two Tier-3 leaf specialists, DocumentAnalyzer and DataAnalyzer, read and extract from already-downloaded material; DataAnalyzer alone holds the tool for extracting structured data such as tables and code. Two additional roles, FindingsWriter and Builder, are never dispatched by the Planner. They are dispatched directly by the completion-check system described in Section 3, in a fresh context, once the Planner's delegation phase has produced sufficient material. FindingsWriter assembles `findings.md` from the run's structured, already-verified results; Builder writes the final report from `findings.md`. Each output receives an independent review pass from a separately instantiated PeerReviewer agent, with one corrective re-dispatch permitted if the review flags a problem.

Tool access is deliberately withheld from each parent role so that it cannot short-circuit the chain it is meant to delegate through. The Planner has no file-writing tool: it cannot produce `findings.md` or the final report itself under any circumstance. This is the first instance of a pattern that recurs throughout the system: rather than instruct a role not to do something, remove its ability to do it.

This architecture also addresses a context-management problem specific to a Planner whose conversation grows monotonically across a run, since the underlying agent framework performs no compaction. Before the fresh-context FindingsWriter/Builder pattern was introduced, every completion-check retry meant re-showing the Planner its own prior rejected drafts inside its own growing conversation, a pattern we term context poisoning: attention degrading on a long, self-referential history well before any hard token limit is reached. Dispatching a fresh-context writer role directly, instead of feeding the retry back through the Planner's conversation, avoids this. Only one class of completion-check failure, indicating that further research needs to be delegated rather than that an artifact needs rewriting, still escalates back to the Planner, since only the Planner can decide what new work to delegate.

## 3. The Verification Layer

The verification layer is a system of deterministic, non-generative checks and dispatch patterns that catch known failure modes after they occur but before they propagate to the next stage of the pipeline, without relying on the model's own judgment to detect its own errors. We describe seven mechanisms in the order in which they compose across a run. Each was motivated by a specific incident, not designed speculatively against an abstract taxonomy of possible agent failures — cf. Cemri et al.'s (2025) MAST taxonomy of recurring multi-agent failure modes, a general classification this project's checks were not derived from but which several turned out to instantiate specific modes of after the fact.

### 3.1 Priority-Ordered Structural Checks with Starvation Guards

At the core of the system is a set of 27 independent, pure-function checks organized into two tiers: 10 completion checks, evaluated first, and 17 grounding checks, evaluated only once the completion-check tier returns no problem. Within each tier, checks are evaluated first-match-wins against the run's actual structured state, producing exactly one verdict per attempt. Each check targets one specific, previously observed failure mode against ground-truth run state rather than a generic classification scheme applied uniformly.

This design introduced its own failure mode, starvation. A first-match-wins priority queue lets any single check near the top of the queue permanently starve every check below it for a run's entire retry budget, if that top check keeps re-firing on state that has not meaningfully changed between attempts. This shape recurred eight times before we generalized a fix: every non-self-resolving check now caps its own consecutive-firing count through a shared helper, and a standing audit test fails automatically if a newly added check omits the cap. The fix draws on two established patterns rather than an invented mechanism: operating-system scheduler aging, in which a starvation counter forces a lower-priority task to receive a turn once a threshold is crossed, and the circuit-breaker pattern, which stops retrying a failing path after a bounded number of attempts (Nygard, 2018). Two of the eight recurrences were caught by the standing audit test before they caused a live failure.

That generalized fix later proved insufficient on its own, which confirmed the starvation shape was a genuine recurring problem class rather than a single bug. A separate incident showed that a completion-check-tier problem recurring indefinitely could permanently prevent a grounding-check-tier detector, built to catch dropped facets in a report, from ever receiving a turn, even though every check inside each tier was correctly capped in isolation. The fix required no new machinery, only a second application of the existing yield mechanism at the boundary between the two tiers. A structural fix scoped to checks within one list does not automatically extend to tiers of lists; the actual boundary of a starvation-prevention mechanism has to be checked explicitly rather than assumed correct because a version of it already shipped once.

### 3.2 Fresh-Context, Independent Review

FindingsWriter and Builder each dispatch to a separately instantiated PeerReviewer agent with zero shared conversation history, rather than performing a self-critique step inside the same context that produced the artifact. This distinction is not stylistic. Reflexion (Shinn et al., 2023) and Self-Refine (Madaan et al., 2023), the self-correction patterns most surveyed multi-agent frameworks default to, both use same-context self-critique, a pattern subsequent survey work identifies as unreliable under a range of conditions (Kamoi et al., 2024), motivating an independent critic in place of self-evaluation. Our design arrived at fresh-context, independent review before this literature comparison was made; the comparison served as confirmation of a choice already forced by production incidents, not as the design's origin.

### 3.3 Deterministic Salvage for Known Failure Shapes

When a writer dispatch produces a genuinely empty response twice in succession, observed live with FindingsWriter returning empty on 6 of 8 attempts within a single run, the system does not simply retry and hope. (A 2026-08-18 refinement bounded this to an initial attempt plus two retries before salvage fires, rather than firing after the second consecutive empty response as originally implemented; the incident and the salvage rationale below are unchanged.) It assembles `findings.md` directly from the run's already-verified structured data, with no further LLM involvement for that artifact, rather than continuing to burn the retry budget on a failure mode already shown to be persistent within that run. This mirrors the core mechanism of Corrective RAG (Yan et al., 2024) and Self-RAG (Asai et al., 2023): both filter or construct evidence structurally before a generator sees it, rather than annotating a detected problem and hoping a subsequent generation step honors the annotation. We arrived at this mechanism independently, from the live incident, and confirmed the parallel against these papers only afterward.

### 3.4 Structural Exclusion Over Embedded Warnings

Rather than trust the model to honor a warning embedded in its own evidence, the system structurally excludes any finding whose own summary carries a verification or relevance warning marker from ever reaching FindingsWriter's evidence pool. This reverses an earlier design decision that deliberately left flagged findings in place on the reasoning that they might still coexist with usable content. That reasoning was falsified live, twice: a model handed its own embedded warning cited the flagged, bad URL anyway, across seven independent dispatches within a single run.

The fix was researched before it was built. Naming forbidden content inside a "do not cite X" instruction risks priming its reproduction rather than preventing it, an effect Mann et al. (2025) document mechanistically in transformer models under negation load, describing it as ironic rebound: suppressing a concept requires internally activating it, which can prime reproduction instead of avoidance. Negated framings more broadly are shown to produce large, unstable swings in judgment specifically in small open-weight models, up to 76 percentage points between affirmative and negated phrasings of the same question, in an ethical-stance study by Elkins and Chun (2026); the domain differs from citation behavior, but the direction of evidence is consistent. The failure this mechanism addresses has a cited, plausible mechanism, not just an anecdote of a model behaving oddly once.

### 3.5 An Engine-Computed Per-Task Verification Ledger

The closest academic analog to this mechanism is VeriMAP (Xu et al., 2025), in which a planner authors an explicit verification function for each subtask it delegates. Our own established finding, that small local models are unreliable at following new structured-output conventions, argues directly against asking the Planner to author anything of the kind. We instead compute a per-task verification ledger structurally, in the engine, from signals that already exist in the run's state, rather than trusting a new Planner-authored field. This preserves VeriMAP's contribution, that a delegated task should carry its own checkable, independently retriable verification state, while dropping the part of its mechanism our own findings argue cannot be trusted to a local model.

### 3.6 Fresh-Context Production Per Facet

Section 3.2 established that fresh-context review is necessary. A dedicated investigation later found it insufficient on its own for a distinct failure shape: a report that mechanically passed every grounding check while silently answering only about a third of a multi-facet query, because the missing facets were never fabricated, they were simply never produced. We ruled out stale sub-agent context first rather than assuming it: each dispatch constructs a genuinely fresh client, confirmed by reading the dispatch code directly. The mechanism actually responsible is the self-correction blind spot documented by Kamoi et al. (2024): models are measurably worse at correcting errors in their own prior output than at correcting the identical error framed as external input.

A smaller, literature-informed fix was tried first: an explicit edit directive naming exactly what content to add, following the Cross-Context Review framing of Song (2026). This produced a clean negative result. It changed which tool the Builder role called, not what content it produced; the citation ratio stayed unchanged, and by the run's end coverage had gone from about a third of the query to zero coverage of one whole facet, despite an explicit instruction not to touch any other part of the report. The negative result was itself informative: it confirmed the failure was the self-correction blind spot specifically, not a matter of tool choice or wording, before we attempted a larger fix.

The fix that worked dispatches Builder once per under-represented facet, each dispatch a genuinely independent, externally scoped production call in the Cross-Context Review sense, against only that facet's own verified findings. This extends the fresh-context-review principle of Section 3.2 to the stronger claim that production must be fresh-context too, once a single generation call holds more independent facets than it can reliably manage at once. A second literature match, found during scoping rather than after the fix was built, further narrowed the diagnosis: Xu et al. (2026) describe an aggregator-noise failure mode in which individual facts are correct but a merge or synthesis step drops whole clusters of them, distinguishing it from two other long-context failure modes they identify. Per-facet dispatch is our own response to this diagnosis, not a mitigation Xu et al. (2026) themselves test; their own paper mitigates aggregator noise through careful prompt design around a single-stage aggregator rather than a hierarchical or multi-stage approach.

A follow-up isolated A/B test sharpened rather than reopened this diagnosis. A plausible, cheap-to-test contributor to a related but distinct failure, a writer role narrating its intended action instead of calling the file-write tool, was the presence of a deliberate-before-acting prompt block. Karmakar and Chatterjee (2026) report a directly relevant negative result with structured prompting on 16 open-weight models: a plan-execute-submit phase decomposition, instructing a model to plan before executing, hurt performance on every model tested, with trace inspection showing at least one model (`ministral-3:8b`, blocked rather than disqualified in our own bake-off, by an unrelated upstream tool-call serialization bug, but which separately showed this same narration-instead-of-write behavior in one run) complying with a "do not call any tools yet" planning instruction and then emitting a prose answer without ever entering the execute phase. A faithful, isolated harness reusing the real evidence base and tool schema from that same model ran nine repetitions with our own project's prompt block present and nine with it stripped: nine of nine real tool calls occurred in both conditions, with no measurable difference. This is a genuine negative result for the specific block we tested: it is not implicated in this failure mode in our harness, and since an isolated single-turn dispatch converges cleanly regardless of its presence, the actual variable is specific to a full run's multi-turn or retry dynamics rather than to prompt content alone, consistent with Karmakar and Chatterjee's finding that the effect is a full-workflow phenomenon.

## 4. Evaluation

Every mechanism in Section 3 was originally validated the same way: implement it, re-run the benchmark that exposed the bug, and confirm the target symptom did not recur in one live trial. This is a real check, but it does not distinguish a genuinely load-bearing fix from an addition that happened to coincide with an unrelated convergence in that run, the audit gap Jwalapuram et al. (2026) identify across multi-agent systems generally as "expensive witnesses": complexity that carries real overhead but contributes near-zero measured effect on the outcome.

We applied a controlled ablation to two accumulated completion-check mechanisms, `force_whole_rebuild` and a `no_progress_guard` added the day before, using an adaptive-trial protocol of one run per condition, escalating to additional runs only when an early disagreement required resolution. The benchmark score reported below is produced by the project's own eval harness (`eval/evaluate.py`): a weighted-criteria rubric scored in [0, 1] per run, where each criterion (an exact-match check, a regex check, or an LLM-judge check, independently weighted) contributes its weight to the score if met, against a fixed evaluation query held constant across every ablation run.

| Mechanism disabled | Mean benchmark score | Runs | Failure pattern |
|---|---|---|---|
| `force_whole_rebuild` | 0.25 (baseline 0.75) | 3 | Same underlying coordination failure the mechanism exists to prevent, in both failing runs |
| `no_progress_guard` | 0.125 (baseline 0.75) | 2 | Both runs timed out, for two distinct specific reasons |

Both mechanisms were confirmed genuinely load-bearing rather than expensive witnesses. The raw per-run scores and the escalation decision are retained in the project's own repository (`eval/ablation_results.jsonl`, `eval/ablation_configs/`) and version-control history, rather than resting solely on this paper's own retelling of them. This is the first controlled-ablation evidence for any mechanism in our completion-check pipeline, in contrast to the single-live-trial validation the remaining five mechanisms in Section 3 still rest on. The larger remaining mechanisms, per-facet dispatch and the starvation guards of Section 3.1, have not yet been put through the same ablation protocol. We report this as a concrete, scoped, and not-yet-executed next step, not as a claim that the unablated mechanisms are unproven in every other sense; each still has live-incident evidence behind it, described in Section 3.

The adaptive-trial protocol itself is a limitation worth naming directly rather than leaving implicit: with n=2 and n=3 runs per condition and an escalation rule triggered by "an early disagreement," these are not pre-registered sample sizes, and no variance or confidence interval is reported alongside the means. The 0.75-to-0.25 and 0.75-to-0.125 gaps are large enough that we are confident the direction is real, but the ablation should be read as strong suggestive evidence at this run count, not as a statistically powered result.

## 5. Related Work

We assess novelty at two levels, because conflating them produces an inaccurate claim in either direction.

At the level of individual components, none of the mechanisms in Section 3 is new. Deterministic verification over agent output exists in industry tooling, most closely a coding-agent pattern using deterministic test pass/fail as its verification signal rather than an LLM judge. Retrieval-grounded citation attribution verification is active published research (Choi et al., 2025). Independent-context critics outperforming same-context self-critique is an established finding (Section 3.2). Small, frozen classifiers replacing LLM judgment for a routing decision is precedented by RouteLLM-style routing (Ong et al., 2024). A separated citation-verification pipeline stage exists in at least one major published system, Anthropic's CitationAgent (Anthropic, 2025).

At the level of the specific combination, we find no documented precedent in the systems we surveyed. Every system we examined implements one of two shapes: same-context or same-loop LLM-as-judge critique, in some cases with a single deterministic routing branch attached, as in LangGraph's Corrective RAG pattern, but never a deterministic check as the primary verification mechanism; or no documented verification mechanism at all for this specific problem, as with Perplexity's retrieval engineering, and OpenAI's Deep Research system card, which is scoped to safety and red-teaming rather than architecture. No system we surveyed combines a dozens-strong, priority-ordered, empirically motivated bank of independently named checks, a starvation guard for that priority queue, and a regression test pinning the verification logic itself against silent merge errors, a real concern in this project's own history, where two checks' branches once silently merged and were only caught by a matrix test with distinctive per-branch assertions, all built consistently for the local, sub-30B-model regime, where every other system we surveyed assumes a frontier-class or well-resourced generator.

Given both levels together, we characterize the contribution as a disciplined, unusually deep combination of known techniques applied to an underserved regime, not an invention of verification for LLM agents from first principles. One residual gap is stated explicitly rather than elided: one AG2 notebook, the example most likely to show genuine tool-grounded deterministic feedback within that framework, returned a repeated fetch failure during our research pass and was never independently verified. We flag it as an open item, worth a targeted follow-up if a specific AG2 comparison becomes load-bearing for a future claim.

## 6. Limitations

We state these plainly rather than softening them, since the honesty of a verification layer's own self-report is part of what such a layer is for.

The empty-response tendency described in Section 3.3 is mitigated in its consequences but not resolved at the model level. The salvage path prevents a doubly empty dispatch from costing a retry cycle; it does not explain, and does not fix, why a fresh dispatch sometimes returns nothing at all. The frequency of this behavior is not consistently reproduced across runs and remains unquantified.

The per-task verification ledger described in Section 3.5 still produces exactly one whole-run verdict per completion-check attempt. A flagged task's directive names the specific problem, but redelegating that task still routes back through the Planner's own turn rather than through an independent, bypassing dispatch that could act on the flag directly. A deeper version of this mechanism was scoped, evaluated against real historical run data, and closed as a no-go: an audit of every run where the ledger flag fired found no clean, unconfounded case of the same task recurring three or more times under a normal retry budget with the directive-only fix genuinely failing, every observed recurrence traced back to an already-fixed, independent root cause. The directive-only version stands as the settled answer unless a future clean run reopens the question under that same specific trigger. This is, to our knowledge, the only structural intervention in the project's incident history that was designed, evaluated, and explicitly abandoned as ineffective; we did not conduct an exhaustive audit of commit and test history for other attempted-and-dropped fixes beyond this one, so the seven-mechanism incident corpus in Section 3 should be read as a record of what was built and kept, not as a complete account of everything that was tried.

Nor is the seven-mechanism account a complete inventory of this failure class in the same subsystem: a synthesis-nudge fix for zero-trailing-text specialist dispatches, and further verification-ledger overlap-detection landmines beyond the one described in Section 3.5, exist in the project's history and are of the same reactive-verification character as the seven mechanisms above, but fall outside this paper's scope.

The verification layer adds real overhead that this paper does not quantify. Fresh-context PeerReviewer dispatch (Section 3.2), per-facet Builder dispatch (Section 3.6), and 27 structural checks evaluated on every attempt all cost additional tokens and wall-clock time beyond a hypothetical no-verification baseline, on hardware that is already VRAM-constrained. We report the reliability gain this buys (Section 4) without a matched cost figure for the overhead side of that trade, which limits how directly a reader can judge whether the trade is worthwhile for a given deployment.

Most fundamentally, the verification layer described here is reactive rather than proactive. Every check fires after a problem has already been generated, catching it before it propagates further, not preventing the underlying model from generating the problem in the first place. This is a deliberate scope choice, matching our repeatedly confirmed finding that architecture and verification amplify a capable model rather than rescue an incapable one. It means the approach has a hard ceiling: below some model capability floor, no amount of downstream checking produces a usable result. What it can still guarantee, at and below that floor, is an honestly labeled failure rather than a silently accepted bad one, which we regard as the correct achievable target for this regime.

This paper is an internal synthesis, sourced from the project's own commits, tests, and a dedicated but time-bounded research pass. It has not been externally peer-reviewed.

## 7. Conclusion

Our central finding is a negative one, reached the hard way: on a local, sub-30B-parameter model, instructing the model to behave reliably does not make it reliable, regardless of phrasing or how explicitly the specific failure is named to it. What works is removing the model's ability to bypass a constraint, or checking its output with code that runs regardless of compliance. The seven mechanisms in this paper, priority-ordered structural checks with starvation guards, fresh-context independent review, deterministic salvage, structural exclusion, an engine-computed verification ledger, per-facet fresh-context production, and a controlled ablation for two of these, are the result of applying that principle consistently across a real system's incident history. None is individually new. Applied together, hardened against a specific underserved hardware regime, and validated wherever possible against real production failures rather than synthetic approximations of them, we believe the combination is. Extending the controlled-ablation discipline of Section 4 to the remaining, larger mechanisms is the most immediate next step this work leaves open.
